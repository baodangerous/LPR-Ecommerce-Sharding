Interpretation
EMA filter
Removing EMA causes migrations to spike to 102 — equal to Reactive's worst-case. Raw load signal is too noisy: transient spikes trigger false-positive migrations. EMA acts as a low-pass filter, suppressing short-term variance and keeping the signal stable.
Growth Rate
Without Growth Rate, migrations rise to 89 and IR worsens. GR measures load acceleration — detecting a shard trending upward before it crosses the threshold. This shifts the intervention point 3–5 cycles earlier than EMA alone would allow.
Cost-Benefit gate
Removing the gate causes migrations to rise to 93. Full LPR achieves 0 unnecessary migrations — the gate correctly identifies that no migration is profitable enough to justify network transfer cost on this workload. This is the primary anti-thrashing mechanism.
Sensitivity analysis over Zipfian workload with cost_barrier = 1.2. The Cost-Benefit gate blocks all migrations across the entire parameter sweep — migration count stays 0. Variation in throughput reflects EMA/GR computation overhead per cycle. The α=0.3 default is chosen for stability, not maximum throughput: it suppresses short-term noise better, which is the design goal in volatile E-commerce workloads.

Why CPU, not GPU
This simulation
Apache PySpark on Google Colab CPU runtime. Sharding logic is hash routing, load monitoring, and scheduling — all CPU-bound. No matrix operations involved.
Production systems
Cassandra, MongoDB, DynamoDB, and all major distributed databases run on CPU server clusters. Data routing and rebalancing have no GPU-accelerable components.
GPU applies to
Deep learning, matrix multiplication, and vector operations. PSAP uses GPU-assisted RL training. LPR's four closed-form equations require no such hardware.
